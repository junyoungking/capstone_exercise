# Mc2 원판 고르기

## 상태

**완료 기준 미달이다. 선택 기능은 기본값을 꺼 두었다.** `--plate-pick`으로 확인된 원판 선택을 켤 수 있고 `--no-plate-pick`으로 끌 수 있다. 확인된 원판을 움직임으로 고르면 조건 밖의 `stu6_11_2/3`과 `stu10_11`이 개선되지만, 조건 안에서 기존에 정확했던 세 영상이 틀려진다. `user_clip_3` 첫 rep도 복구하지 못했다. 완료 기준이 충족되지 않은 설정을 제품 기본값으로 사용하면 회귀가 생기므로 opt-in이다.

## 규칙과 실행

`TrackCfg.plate_pick`은 기본 `false`다. `python -m server.jobs VIDEO --exercise squat --model MODEL --plate-pick`, `python -m server.compare --user VIDEO --exercise squat --out OUT --plate-pick`, `python -m server.app --plate-pick`으로 켠다. `--no-plate-pick`은 명시적으로 기존 경로를 선택한다. `--plate-pick-weak`은 별도 실험이며 선택 기능도 함께 켠다. 기준 영상 캐시 키에 두 설정이 모두 들어간다. 지름은 선택 알고리즘의 입력이 아니므로 `plate_mm`을 바꾸어도 선택은 바뀌지 않는다.

첫 패스에서 기존 ONNX 검출을 프레임당 한 번만 실행하고 결과를 메모리에 보관한다. 후보 상자는 기존 `score_low` 이상만 쓰며, 0.75초 이내의 다음 검출을 기존 중심 거리 `gate=0.5`와 크기 비율 `0.75~1.33`으로 일대일 연결한다. 낮은 점수로만 된 묶음은 기본 선택 대상이 아니다. 높은 점수(`score_high=0.3`)가 한 번이라도 있는 묶음만 확인된 원판이다. 이동량은 묶음의 세로 중심 5~95백분위 범위를 검출 상자의 중앙 지름으로 나눈 값이며, 관측이 세 개 미만이면 움직임 근거가 없는 것으로 둔다. 0.29 지름 이상인 확인된 묶음이 있고 기존 선택 묶음은 그렇지 않을 때 움직이는 묶음을 고른다. 복수이면 최초 확인 프레임과 그 프레임의 점수×넓이로 정한다. 고른 묶음의 첫 약한 검출부터 두 번째 패스에서 기존 KLT를 시작한다. 기존 선택과 시작이 같으면 기존 추적 코드를 그대로 실행한다.

추가 검출 모델 실행은 없고, KLT·상태기계·검출 임계값·Mc의 `recover_early_back`은 바꾸지 않았다. 선택을 켠 경우 진행률은 실제 검출 패스와 실제 추적 패스의 처리 프레임을 합쳐 표시한다. `--plate-pick-weak`은 높은 점수가 없어도 6개 이상 검출이 1초 이상 이어지고 0.29 지름 이상 움직인 묶음을 시험한다. 이것은 기본값 후보가 아니다.

## 평가 방법과 한계

Mc와 같은 61개 + team9 9개 + 내 분리 클립 4개에서 중복 `stu8_7`을 한 번만 센 73개, 연결 영상은 별도다. 연결 전 클립은 Mc에서 만든 영상과 요청된 GT를 그대로 사용한다. 저장된 프레임별 검출을 새 선택기와 실제 영상의 KLT에 재생했다. 기록에 검출이 10개 이상인 프레임은 없으므로 저장 시 상위 10개 제한에 걸린 프레임은 없다. 이벤트 매칭은 ±0.5초다. `stu3_64`는 19회 정답 중 종료 시각 라벨이 미완성이어서 이벤트 지표에서만 제외했다. 원판 상자 비율과 자막 확인으로 분류한 촬영 조건은 Mc의 한계도 그대로 가진다.

### 남은 실패와 회귀

- `GB_S07_R12`: 4 → 0프레임으로 시작하면서 화면 아래가 잘린 약한 검출을 신호에 포함한다. 후속 추적은 사실상 같아도 신호 경계가 달라져 완료 이벤트가 1 → 0이 됐다. `images/edge_regression.jpg`에서 상자가 화면 끝에 걸린 모습을 확인할 수 있다.
- `GB_S07_R14`, `GB_S07_R20`: 첫 후보 묶음이 짧은 검출 공백으로 끊겼다. 선택기는 짧은 첫 묶음이 정지한 것으로 취급하고 나중 묶음으로 시작했다. 이 때문에 이전에 맞던 완료 횟수 1이 0이 됐다. 움직이는 원판을 다른 정지 원판으로 잘못 판별한 사례다.
- `user_clip_3`: 111 → 110프레임으로 한 프레임만 앞당겨졌고 첫 rep은 그대로 누락됐다. `images/clip3.jpg`는 양쪽 모두 첫 rep 바닥 부근에 시작하는 모습을 보여 준다.
- `stu6_11_2/3`: 보관된 노란 원판 대신 움직이는 바의 원판을 선택해 각각 0 → 4, 0 → 1회가 됐다. `images/stored_plate.jpg`에서 선택 대상을 확인했다.
- `stu10_11`: 0 → 20회이며 이벤트는 19 TP, 1 FP, 1 FN이다. `images/bench_detection.jpg`는 시작 프레임의 선택 차이를 보여 준다.
- `stu3_64` 등 나머지 오류와 GT 한계는 Mc 보고서 및 `evaluation.json`에 남아 있다. 합산 개선으로 개별 영상의 회귀를 가리면 안 된다.

## 속도·시험

같은 61.5초 연결 영상, 1477프레임, CPU ONNX 6스레드, OpenCV 1스레드로 한 번씩 순차 측정했다. 선택 끔은 37.84초, 켬은 36.19초였다 (`timing.json`). 두 번째 측정의 워밍업과 시스템 변동이 포함된 단일 측정이므로 속도 향상을 주장할 수 없고, 검출 후 추가 디코드 비용이 존재한다. `server.compare --plate-pick` 실제 분석도 실행돼 `user_clip_3`에서 1회 결과가 나왔다.

선택을 끄고 75개 실제 영상을 저장 검출로 다시 추적한 원판 JSONL의 **압축 해제 바이트**는 Mc 기록과 75/75 같았다 (`bytecheck.json`). 선택을 켰을 때 같은 원판과 시작 프레임을 쓴 44개 영상도 기존 행과 같았다. 나머지는 선택이나 시작이 바뀌었다. 합성 시험은 약한 앞부분과 높은 점수의 연결, 약한 바닥 물체, 정지/움직이는 원판, 가까운 큰 원판, 정지 후보, 설정 끄기 및 탐지 1회, 불연속과 약한 전용 실험을 다룬다.

- `cd plate_pipeline && python -m pytest -q tests eval/midterm/test_metrics.py`: 205개 통과, Starlette 경고 1개.
- 저장소 루트 `python -m pytest -q tests/fb`: 235개 통과. 시스템 PATH에 node가 없어 Playwright에 설치된 node 경로를 추가해 재실행했다.
- sim 경로·판정 숫자는 바꾸지 않아 sim은 재실행하지 않았다.
