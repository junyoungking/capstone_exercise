# 3대 운동 기록·피드백 파이프라인: 진행 상황과 계획 (2026-10-26)

## 1. 프로젝트 한 줄 요약

옆에서 찍은 스쿼트·벤치·데드리프트 영상에서 **원판 위치**를 따라가서 횟수, rep별 값(깊이, 내리는·멈춘·올리는 시간, 평균 속도)을 기록한다. 세트 안의 변화와 기준 영상과의 차이를 판정어 없는 문장으로 알려 준다.

- 1차 신호는 원판이다 (지름 450 mm로 cm 환산). 포즈는 보조다.
- 설계 문서는 Claude Docs "3대 운동 기록·피드백 파이프라인 — 처음부터 설계"다. 탭은 파이프라인, 구현 설계, 근거·출처, 반복 기록 넷이다.
- 코드는 GitHub `junyoungking/capstone_exercise`의 **`plate-pipeline` 브랜치, `plate_pipeline/` 폴더**에 있다. main은 건드리지 않는다.
- 저장소 루트의 예전 YOLO 바벨 검출 코드(`model/extract_barbell_yolo_world.py` 등)는 잘 안 돼서 쓰지 않는다. 보지 않는다.

## 기말 목표와 마일스톤 (2026-10-26 결정, 지금 기준)

**바뀐 결정 (10-21 통합 단계 결정을 고침):**

- 3D: 선택 → **필수**. 리프터 2D를 VideoPose3D(H36M-17, `track3d/` 재사용, CC BY-NC 4.0이라 비상업만)로 올린다. 데모처럼 다듬고, 뼈 길이를 고정하고, 원판으로 잰 키로 크기를 맞춘다.

**feedback-ui 브랜치 확인 (2026-10-22, c6f08e8):**
- 내용 (기준 문서는 그 브랜치의 `docs/design.md`):
  - 스쿼트 데모다. 입력은 사용자 영상과 기준 영상 1 rep이다.
  - 포지션 5개(시작·하강 중간·바닥·상승 중간·락아웃) × 지표 5개(무릎각·엉덩이각·몸통 기울기·발바닥 밀착·머리-엉덩이)와 템포를 비교한다.
  - rep마다 목표를 하나 고르고, 템플릿 문장으로 말한다 (판정어 금지).
  - 정적 HTML 리포트, 2D 골격, 3D 보기, 실패 화면이 있다.
- 시험:
  - `tests/fb` 187개가 NumPy 2.2에서 통과한다.
  - NumPy 2.5에서는 `unified_feedback_v4.py:971`의 2차원 `np.cross` 때문에 실패한다. S2에서 고친다.
- 공개 스쿼트 샘플로 돌려 봄:
  - 원판 key times로 라벨을 만들어, 수동 라벨 없이 리포트까지 나왔다.
  - 이 영상은 발이 화면 밖이고 원판이 상체를 가린다. 포즈 칸 대부분을 못 쟀다.
  - 기준 rep 3은 잴 수 있는 칸이 24%라 입력 검사에서 막혔다 (정상 동작).
  - 제외 기준을 낮춰 돌리면 같은 사람의 rep끼리 "머리-엉덩이 −121% (k 6.7)"가 나온다. 포즈 오검출이다. 그래서 리포트를 남에게 보이기 전에 S3이 필요하다.
- 결정:
  - 포지션은 원판 높이로 정한다 (쉼 → 중간 → 먼 점 → 중간 → 쉼).
    - 엉덩이 높이 규칙은 스쿼트만 되고, 수동 라벨이나 ST-GCN이 있어야 한다. 그래서 예비로 둔다.
  - 템포는 원판 key times(내림·먼 점 멈춤·올림)로 재고, 원판 비교 규칙으로 판정한다. feedback-ui의 템포 임계(0.3/0.2/0.3초, 임의값)는 쓰지 않는다.
  - 비교 화면은 feedback-ui 리포트 구성을 쓴다. 색과 글자는 `docs/DESIGN.md`로 맞춘다 (S5).
  - 분석과 보기는 같은 파일 하나로 한다. 그래야 원판 분석, 포즈, 리포트 재생의 프레임 번호가 하나가 된다 (2026-10-22, S2 프롬프트에서 고침).
    - 브라우저에서 안 되거나 회전·가변 fps인 영상만 H.264 CFR 사본을 만든다. fps는 원래 평균 fps를 유지한다.
    - 지금 `tools/check_video.py --fix`는 30 fps로 바꾼다. 60 fps 영상의 속도·템포 해상도를 잃으므로 기본으로 쓰지 않는다.
  - `feedback-ui`는 S2를 시작할 때 `plate-pipeline`에 합친다. 시험 병합에서 충돌은 없었고 `.gitignore`만 자동으로 합쳐졌다.

### 1단계: 코어와 합성 시험 (`core/`, `sim/`)
- 신호 처리(이상치 제거, 공백 보간, 5 Hz 필터), 라이브 계산, 상태기계(진입 6 cm, 최소 폭 13 cm, 복귀 70%), 부분 rep, 다른 자리, 리랙을 짰다.

- 합성 생성기를 다시 만들었다 (반복 1~17의 코드는 지워졌음). 깨뜨리기 41가지, 임계값 스윕도 다시 짰다.
- 결과:
  - 횟수: 15조건 중 12조건이 문서와 같다.
  - 속도 RMSE: 30 fps, 잡음 1 cm에서 0.033 m/s.
  - 깨뜨리기: 27가지 중 26가지가 0.995 이상.
  - 두 세트 시험: 0.995 이상. 같은 종목은 간격 44초 안팎에서 나뉜다.
  - 마지막 rep 실패: 1.000.
  - 횟수가 오르는 시점: 바가 다 돌아오기 0.31초 전.

### 2단계: 비교와 문장 (`core/compare/`, `core/text/`)
- 판정식은 |δ| > k·SE이고 |δ| ≥ 최소 변화량이다. k는 값의 수마다 정한 표(`core/crit_table.json`, 값 하나의 거짓 2.5%)에서 읽는다. 산포는 2차 차분으로 구한다.
- 세트 안 비교: 먼 점 거리, 내리는 시간.
- 기준 영상 비교: 내리는 시간, 먼 점에서 멈춘 시간.
- 문장: 템플릿만 쓴다. 판정어가 없고, 최대 3개를 보여 준다. LLM 다듬기는 기본으로 꺼져 있다.
- 새 생성기로 다시 맞춘 결과: 거짓 비율은 값 하나 ≤2.4%, 리포트 ≤3.7%.
  - 예외: 기준 영상이 1 rep이면 1.8~4.4%. 첫 rep을 더 크게 틀리게 재기 때문이다.
  - 검출은 고정 배수 규칙보다 낮다. 마지막 2 rep이 4 cm 덜 내려간 세트를 8~19%만 잡는다.
