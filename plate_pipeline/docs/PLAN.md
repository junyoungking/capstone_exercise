# 3대 운동 기록·피드백 파이프라인: 진행 상황과 계획 (2026-10-22)

## 1. 프로젝트 한 줄 요약

옆에서 찍은 스쿼트·벤치·데드리프트 영상에서 **원판 위치**를 따라가서 횟수, rep별 값(깊이, 내리는·멈춘·올리는 시간, 평균 속도)을 기록한다. 세트 안의 변화와 기준 영상과의 차이를 판정어 없는 문장으로 알려 준다.

- 1차 신호는 원판이다 (지름 450 mm로 cm 환산). 포즈는 보조다.
- 설계 문서는 Claude Docs "3대 운동 기록·피드백 파이프라인 — 처음부터 설계"다. 탭은 파이프라인, 구현 설계, 근거·출처, 반복 기록 넷이다.
- 코드는 GitHub `junyoungking/capstone_exercise`의 **`plate-pipeline` 브랜치, `plate_pipeline/` 폴더**에 있다. main은 건드리지 않는다.
- 저장소 루트의 예전 YOLO 바벨 검출 코드(`model/extract_barbell_yolo_world.py` 등)는 잘 안 돼서 쓰지 않는다. 보지 않는다.

## 2. 구현 순서와 상태

| 단계 | 내용 | 완료 기준 | 상태 |
|---|---|---|---|
| 1 | 합성 시험 도구 + 신호·판정 코어 | 반복 16 수치를 표본 오차 안에서 재현 | **끝** |
| 2 | 비교와 문장 (세트 요약, 배수 표, 판정, 템플릿, 숫자 대조) | 배수 표 = 문서 표, 정규분포 시험 값 하나 거짓 ≤2.5%, 판정어 0 | **끝** |
| 3 | 업로드 경로 (영상 → 원판 검출 → 횟수·값 → 기록 → 리포트, 종목은 사용자가 고름) | 자기 세트 20개 횟수 일치 + 리포트. 원판 재현율 ≥95% (벤치 따로), 위치 잡음 ≤0.5 cm | **진행 중**: 코드·학습·평가 스크립트 끝. 촬영·라벨·학습·측정이 남음 |
| 4 | 방향과 종목 (바닥 검사, 프레임 분류기, "확인 필요") | 정답 세트 60개에서 틀린 방향 0, 확신하고 틀린 종목 0 | 아직 |
| 5 | 실시간 (서버, 폰 전송, 두 번째 화면, 라이브 계산, rep 직후 속도) | 25 fps 이상, 화면 지연 p95 횟수 0.5초·속도 1.5초, 라이브=최종 98% | 아직 |
| 6 | 비교 화면과 기준 영상 | 같은 템포 30쌍 중 "다르다" ≤3쌍, 1초 차이 30쌍 중 ≥24쌍 | 아직 |

4~6단계의 일은 아래 통합 단계(S)로 옮겼다. 완료 기준은 위 표를 그대로 쓴다.

### 통합 단계 (2026-10-21 결정)
예전 학기 포즈 파이프라인에서 쓸 것만 끼운다. 원판이 1차 신호이고, MediaPipe 포즈는 보조다. 포즈는 사람 고르기, 바닥 검사의 발, 종목 분류기 입력, 골격 그림, 손목 보조에만 쓴다. 예전의 각도 판정, 단계 비율 정렬, LLM 생성은 버린다.
구현은 다른 에이전트가 한 단계씩 `integ/<단계>` 브랜치에서 한다. 검증한 뒤 `plate-pipeline`에 합친다.

**feedback-ui 브랜치 확인 (2026-10-22, c6f08e8):**
- 내용 (기준 문서는 그 브랜치의 `docs/design.md`):
  - 스쿼트 데모다. 입력은 사용자 영상과 기준 영상 1 rep이다.
  - 포지션 5개(시작·하강 중간·바닥·상승 중간·락아웃) × 지표 5개(무릎각·엉덩이각·몸통 기울기·발바닥 밀착·머리-엉덩이)와 템포를 비교한다.
  - rep마다 목표를 하나 고르고, 템플릿 문장으로 말한다 (판정어 금지).
  - 정적 HTML 리포트, 2D 골격, 3D 보기, 실패 화면이 있다.
- 시험:
  - `tests/fb` 187개가 NumPy 2.2에서 통과한다.
  - NumPy 2.5에서는 `unified_feedback_v4.py:971`의 2차원 `np.cross` 때문에 실패한다. S2에서 고친다.
- 공개 스쿼트 샘플로 돌려 봄:
  - 원판 key times로 라벨을 만들어, 수동 라벨 없이 리포트까지 나왔다.
  - 이 영상은 발이 화면 밖이고 원판이 상체를 가린다. 포즈 칸 대부분을 못 쟀다.
  - 기준 rep 3은 잴 수 있는 칸이 24%라 입력 검사에서 막혔다 (정상 동작).
  - 제외 기준을 낮춰 돌리면 같은 사람의 rep끼리 "머리-엉덩이 −121% (k 6.7)"가 나온다. 포즈 오검출이다. 그래서 리포트를 남에게 보이기 전에 S3이 필요하다.
- 결정:
  - 포지션은 원판 높이로 정한다 (쉼 → 중간 → 먼 점 → 중간 → 쉼).
    - 엉덩이 높이 규칙은 스쿼트만 되고, 수동 라벨이나 ST-GCN이 있어야 한다. 그래서 예비로 둔다.
  - 템포는 원판 key times(내림·먼 점 멈춤·올림)로 재고, 원판 비교 규칙으로 판정한다. feedback-ui의 템포 임계(0.3/0.2/0.3초, 임의값)는 쓰지 않는다.
  - 비교 화면은 feedback-ui 리포트 구성을 쓴다. 색과 글자는 `docs/DESIGN.md`로 맞춘다 (S5).
  - 분석과 보기는 같은 파일 하나로 한다. 그래야 원판 분석, 포즈, 리포트 재생의 프레임 번호가 하나가 된다 (2026-10-22, S2 프롬프트에서 고침).
    - 브라우저에서 안 되거나 회전·가변 fps인 영상만 H.264 CFR 사본을 만든다. fps는 원래 평균 fps를 유지한다.
    - 지금 `tools/check_video.py --fix`는 30 fps로 바꾼다. 60 fps 영상의 속도·템포 해상도를 잃으므로 기본으로 쓰지 않는다.
  - `feedback-ui`는 S2를 시작할 때 `plate-pipeline`에 합친다. 시험 병합에서 충돌은 없었고 `.gitignore`만 자동으로 합쳐졌다.

**2026-10-22 결정 (GPT 쪽 검출기 실험을 보고):**
- 검출기는 YOLOX-Tiny를 유지한다. YOLO26s/m(Ultralytics)은 쓰지 않는다.
  - 공개 시험은 조금 더 좋았지만 실제 영상 횟수가 더 나빴다.
  - 라이선스가 AGPL-3.0이다.
- 검출기는 CPU에서도 돌아야 한다. f47c968의 CUDA 강제는 S1.5a에서 기본 auto로 되돌린다.
- "Track 비율"(plate.used)은 맞는 원판을 따라갔다는 뜻이 아니다. 맞는 원판인지는 손목-원판 상관과 정답 박스 IoU로 따로 잰다.
- 팀 영상 9개는 디버깅에 썼으므로 이제 개발용이다.
  - 마지막 수치는 따로 둔 시험 세트에서 한 번만 잰다.
  - 시험 세트 조건: 다른 사람·세션, 횟수를 두 번 센다, 운동 원판 정답 박스를 0.5초마다 단다.
  - 예전 학기 영상 중 횟수 라벨이 있고 원판이 보이는 것을 더 모은다. 사람(stu 번호) 단위로 개발과 시험으로 나눈다.

## 3. 지금까지 한 것

### 1단계: 코어와 합성 시험 (`core/`, `sim/`)
- 신호 처리(이상치 제거, 공백 보간, 5 Hz 필터), 라이브 계산, 상태기계(진입 6 cm, 최소 폭 13 cm, 복귀 70%), 부분 rep, 다른 자리, 리랙을 짰다.
- rep 값은 끝점 외삽으로 시각 4개를 구한다.
- **세트 닫기**(`core/judge/session.py`): 마지막 rep 뒤 45초 동안 13 cm 넘는 동작이 없으면 닫는다. 종목 라벨이 3초 다르면 닫는다. 라이브는 5초 쉬면 잠정 리포트를 낸다.
- 합성 생성기를 다시 만들었다 (반복 1~17의 코드는 지워졌음). 깨뜨리기 41가지, 임계값 스윕도 다시 짰다.
- 결과:
  - 횟수: 15조건 중 12조건이 문서와 같다.
  - 속도 RMSE: 30 fps, 잡음 1 cm에서 0.033 m/s.
  - 깨뜨리기: 27가지 중 26가지가 0.995 이상.
  - 두 세트 시험: 0.995 이상. 같은 종목은 간격 44초 안팎에서 나뉜다.
  - 마지막 rep 실패: 1.000.
  - 횟수가 오르는 시점: 바가 다 돌아오기 0.31초 전.

### 2단계: 비교와 문장 (`core/compare/`, `core/text/`)
- 판정식은 |δ| > k·SE이고 |δ| ≥ 최소 변화량이다. k는 값의 수마다 정한 표(`core/crit_table.json`, 값 하나의 거짓 2.5%)에서 읽는다. 산포는 2차 차분으로 구한다.
- 세트 안 비교: 먼 점 거리, 내리는 시간.
- 기준 영상 비교: 내리는 시간, 먼 점에서 멈춘 시간.
- 문장: 템플릿만 쓴다. 판정어가 없고, 최대 3개를 보여 준다. LLM 다듬기는 기본으로 꺼져 있다.
- 새 생성기로 다시 맞춘 결과: 거짓 비율은 값 하나 ≤2.4%, 리포트 ≤3.7%.
  - 예외: 기준 영상이 1 rep이면 1.8~4.4%. 첫 rep을 더 크게 틀리게 재기 때문이다.
  - 검출은 고정 배수 규칙보다 낮다. 마지막 2 rep이 4 cm 덜 내려간 세트를 8~19%만 잡는다.

### 3단계: 업로드 경로 (`core/io`, `core/recog`, `core/signal/height.py`, `server/`, `train/`, `eval/`)
- 영상 읽기(PyAV, 회전 반영) → 프레임별 위치 기록(gzip JSONL) → KLT 추적 → cm 환산 → 코어 → HTML 리포트 (`python -m server.jobs`).
- **공개 스쿼트 영상 시험** (GitHub dw2kim/BarbellTrackingCode `test_squat.mov`, 검출기 없이 첫 프레임 박스 + 원판 테두리 원 찾기 + KLT):
  - 4회 맞음.

## 4. 앞으로 할 것

### 3단계 마무리 (지금)
작업 분담: **학습만 GPU 컴퓨터, 나머지는 CPU 컴퓨터.**

1. **촬영 (CPU 컴퓨터 쪽, 사람)**
   - 세 종목을 옆이나 비스듬히 찍는다. 20 kg 원판과 작은 원판을 섞는다.
   - 세션(날짜+장소)을 3개 이상 만든다. 시험용 세션은 장소나 사람이 달라야 한다.
   - 세트마다 실제 횟수를 적는다. 횟수 확인용 세트는 20개다.
   - 쉬는 바를 10초 찍은 클립 1개.
   - 30/60 fps, 슬로모션 끔, 원판 전체가 보이게.
2. **프레임 뽑기:** `python -m train.plate.extract_frames --videos videos.csv --out data/own --per-video 15`
3. **자동 라벨:** `python -m train.plate.autolabel ...` (CPU면 tiny 모델, 느리면 GPU 컴퓨터에서)
4. **라벨 고치기:** `python -m train.plate.review ...`
   - 학습용 약 300장, 시험용 300장.
   - 공개 데이터 Roboflow 659장, 957장은 박스가 원판 테두리를 감싸는지 확인한다.
5. **데이터셋 만들기:** `python -m train.plate.make_dataset ...` → `datasets/plate/`를 GPU 컴퓨터로 옮긴다.
6. **학습 (GPU 컴퓨터):** `python -m train.plate.train --data datasets/plate` → `models/plate_tiny.onnx`를 CPU 컴퓨터로 옮긴다.
7. **측정 (CPU 컴퓨터):**
   - `eval.plate_recall`: 재현율 ≥95%, 벤치 따로
   - `eval.noise`: ≤0.5 cm
   - `eval.counts`: 20세트 전부 일치
8. **결과를 문서에 반영:** 근거·출처 탭, 구현 설계 3단계 진행, 반복 기록 Iteration 18. 기준에 못 미치면 파이프라인 탭 마지막 표의 "다시 여는 결정"부터 고친다.
   - 재현율이 낮으면 원판을 1차 신호로 둘지 다시 정한다.
   - 위치 잡음이 크면 속도 피드백을 넣을지 다시 정한다.
