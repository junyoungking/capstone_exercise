# plate_pipeline

원판 추적 기반 3대 운동 기록·피드백 파이프라인의 구현이다. 설계는 Claude Docs 문서 "3대 운동 기록·피드백 파이프라인 — 처음부터 설계"에 있고, 이 폴더는 그 문서의 구현 설계 탭을 따른다. 1학기 코드(저장소 루트)와는 섞지 않는다.

지금 들어 있는 것은 구현 순서의 1~2단계와 3단계(업로드 경로)의 첫 부분이다. 1단계는 신호 처리, 상태기계, rep 값 계산, 세트 닫기, 합성 시험 도구, 2단계는 세트 요약, 판정 배수 표, 비교 판정, 문장 템플릿과 대조다. 영상을 읽거나 원판을 찾는 부분은 아직 없다.

## 구성

```text
core/
  config.py          설정값 전부 (라이브·최종 신호, 상태기계, 속도)
  signal/final.py    최종 계산: 이웃 이상치 3회 검사, 0.5초 이하 공백 보간, 영위상 버터워스 5 Hz
  signal/live.py     라이브 계산: 처음 5개 중앙값으로 시작, 이상치 게이트, 인과 버터워스 4 Hz
  judge/state.py     상태기계 (진입 6 cm, 최소 폭 13 cm, 복귀 70%, 바운스 0.4초, 미완료 20초, 공백 규칙)
  judge/sets.py      최종 계산의 부분 rep, 다른 자리, 리랙 판정
  judge/session.py   세트 닫기 (마지막 rep 뒤 45초, 종목 라벨 3초, 라이브 잠정 리포트 5초)
  measure/times.py   시각 4개 (끝점 외삽 2*t1 - t2), ROM, 먼 점 거리, 평균 속도, 템포
  crit_table.json    판정 배수 표 A·B·C (sim/crit.py가 만듦, 문서 표와 같음)
  io/video.py        PyAV로 프레임과 시각 (회전 메타데이터 반영)
  io/rows.py         프레임 줄 (gzip JSONL)
  recog/plate.py     원판 검출기 자리 (ONNX, 라벨 박스) + 모델이 없을 때 쓰는 원판 테두리 원 찾기
  recog/track.py     KLT 추적 (원판 고리 부분에만 점, 검출이 가까우면 그쪽으로)
  signal/height.py   프레임 줄 → 바 높이·가로 위치 (m), 프레임마다 원판 크기로 환산
  compare/summary.py 세트 요약: 값별 rep 번호와 값, 2차 차분 산포 (낮은 신뢰도 rep은 빠짐)
  compare/judge.py   세트 안 비교와 기준 영상 비교, 건너뛴 이유
  text/templates.py  문장 템플릿, 순서 (기준 비교 먼저, 비율 큰 순), 3개까지 보이기, none·skip 문장, 측정 요약
  text/check.py      판정어 검사, 숫자·단위·방향 대조, 합니다체 검사
  text/polish.py     LLM 다듬기 (기본 꺼짐, 대조에 걸리면 템플릿 문장으로 되돌림)
sim/
  gen.py             합성 궤적과 관측 (생성기 값은 GEN에 전부 있음)
  scenarios.py       깨뜨리기 상황 41가지 + 따로 돌린 둘
  evaluate.py        코어를 돌려 정답과 비교
  run_base.py        기본 시험: fps x 잡음별 횟수, 잡음별 속도 오차
  run_break.py       깨뜨리기 시험
  crit.py            판정 배수 표 만들기 (정규분포 40만 번, 씨앗 2026)
  run_compare.py     비교 판정 시험: 표 대조, 정규분포 시험, 생성기 시험
  two_sets.py        한 녹화에 두 세트 (같은 종목 / 다른 종목)
  run_sets.py        세트 시험: 두 세트, 마지막 rep 실패, 횟수·속도가 나오는 시점
train/plate/          원판 검출기 학습 (README.md에 순서): 프레임 뽑기, Grounding DINO 자동 라벨, 손으로 고치는 도구,
                      데이터셋 만들기 (세션 단위 분리), YOLOX-Tiny 미세조정, ONNX 내보내기
eval/
  plate_recall.py    시험 프레임에서 원판 검출 재현율 (95%, 벤치 따로)
  noise.py           쉬는 바의 위치 잡음 (0.5 cm)
  counts.py          내 세트들의 횟수 일치
server/
  jobs.py            업로드 처리: 영상 → 프레임 줄 → 최종 계산 → 세트 → 리포트
  report.py          세트 리포트 HTML (문장, 바 높이, rep 표, 템포 막대, 속도)
tests/               pytest 단위 시험
results/             시험 결과 (json)
```

## 실행

```bash
cd plate_pipeline
pip install numpy scipy pytest av opencv-python
python -m pytest -q tests
python -m sim.run_break --sets 600       # 깨뜨리기 41가지 (2코어로 약 10분)
python -m sim.run_base                   # 기본 시험 (2코어로 약 15분)
python -m sim.crit                       # 배수 표 다시 만들기 (약 1분)
python -m sim.run_compare                # 비교 판정 시험 (2코어로 약 10분)
python -m sim.run_sets                   # 세트 시험 (2코어로 약 1분)
python -m server.jobs VIDEO --exercise squat --box x0,y0,x1,y1 --out out   # 영상 하나 처리
```

## 합성 생성기

반복 1~17의 생성기 코드는 2026-10-08 작업 폴더 초기화로 지워졌다. 문서에 남은 설명(세 종목 왕복, 언랙·워크아웃·리랙·가로 움직임, 코사인 올림 75%와 중간에 느려지는 올림 25%, 위치 잡음 두 성분, 탈락 10%, 0.4초 공백 1개, 0.2~1 m 이상치 1%, 프레임 시각 흔들림 ±20%)대로 다시 만들었다. 문서에 없던 값은 아래처럼 정했고 `sim/gen.py`의 `GEN`에도 같은 값이 있다.

| 값 | 설정 |
| --- | --- |
| 세트당 rep | 2~9 균등 |
| ROM (m) | 스쿼트 N(0.527, 0.062) [0.35, 0.70], 벤치 N(0.355, 0.065) [0.22, 0.50], 데드 N(0.53, 0.05) [0.42, 0.65]. rep마다 ±3% |
| 내리는 시간 (세트 기준, s) | 스쿼트 1.2~3.0, 벤치 1.0~2.6, 데드 0.8~1.8. rep마다 ±8% |
| 올리는 시간 (첫 rep, s) | 스쿼트 0.7~1.5, 벤치 0.6~1.3, 데드 0.8~1.5. rep마다 3~10%씩 늘어남, ±8% |
| 먼 점에서 멈춤 (s) | 스쿼트·벤치 0~0.3, 데드(락아웃) 0.3~1.0 |
| rep 사이 쉼 (s) | 스쿼트·벤치 0.5~2.5, 데드 0.8~2.5 |
| 가로 흔들림 | rep마다 최대 ±3 cm |
| 스쿼트 랙 | 거치대 1.25~1.50 m, 언랙 3~10 cm, 워크아웃 12~60 cm (1.5~3초, 세로 출렁임 1.5 cm 이하) |
| 벤치 | 가슴 높이 0.62~0.72 m, 락아웃 = 가슴 + ROM, 거치대 = 락아웃 - 3~12 cm, 가슴 위로 12~30 cm 이동 (0.8~1.5초) |
| 데드 | 바닥 0.225 m (원판 반지름) |
| 앞뒤 여유 | 녹화 시작 후 1~3초, 끝나기 전 1~3초 |
| 위치 잡음 | 프레임마다 독립인 성분 sd + 느린 성분(OU, 시정수 1초) sd/2 |

내리는 시간과 올리는 시간은 문서에 남은 슬로모션 수치에 맞춰 골랐다: 4배에서 배속을 묻는 세트 17%, 8배 97%, 8배에서 횟수가 맞은 세트 0.222. 이 생성기로는 15%, 99%, 0.26이다.

## 문서와 비교 (2026-10-17)

전체 표는 `results/compare.md`, 원자료는 `results/*.json`이다. 생성기를 새로 만들었으므로 숫자가 똑같을 이유는 없고, 같은 방향과 크기인지를 봤다.

- **횟수 (fps 15·30·60 x 잡음 0.3~4 cm, 조건마다 900세트).** 15조건 중 12조건이 표본 오차 안에서 같다. 잡음 4 cm의 세 조건만 이번이 높다 (30 fps 최종 0.991 대 0.976, 라이브 0.952 대 0.887).
- **평균 속도 (30 fps).** RMSE는 잡음 0.2 / 0.5 / 1 / 2 cm에서 최종 0.008 / 0.016 / 0.033 / 0.060, rep 직후 재계산 0.009 / 0.014 / 0.028 / 0.053 m/s (문서 rep 직후 0.015 / 0.021 / 0.036 / 0.070). 편향 중앙값, 10% 넘게 틀린 비율, 공백으로 비운 비율, 계산 안 된 비율은 문서와 1~2%p 안이다 (2 cm의 공백 비움만 8.7% 대 4.5%).
- **깨뜨리기 27가지 (문서: 모두 0.995 이상).** 26가지가 기준 안이다. "벤치: rep 사이에 바를 8~12 cm 고쳐 잡음"만 최종 0.983이다. 0.4초 공백이 12 cm 고쳐 잡기의 먼 점 옆에 걸리면 깊이를 모른다는 예외 때문에 13 cm를 넘긴 왕복이 그대로 세어진다.
- **수치가 적힌 16가지.** 6가지는 같고, 5가지는 이번이 높고, 5가지는 낮다. 낮은 것은 작은 ROM의 고쳐 잡기 세 줄(12 cm 0.040 대 0.193), 매 rep 8~12 cm에서 멈춤(0.983 대 0.998), 녹화가 rep 도중에 시작(0.771 대 0.920)이다.
  - 고쳐 잡기는 잡음이 깊이를 1 cm쯤 부풀리는 정도에 달려 있다. 느린 잡음 성분의 시정수를 0.1~1초로 바꿔도 결과가 거의 같아서, 고쳐 잡는 동작의 모양(바닥에서 0.3~1초 멈춤)이 원래와 다른 것으로 본다.
  - 녹화 시작 위치는 문서에 적혀 있지 않아 첫 rep 전체에서 고르게 골랐다. 앞부분 40% 안에서 잘리면 보인 폭이 중앙값의 60%를 넘어 세어지는데, 정답에서는 뺀다. 설계 문서가 "잘린 rep을 셀지가 모호함"이라고 적은 그 지점이다.
- **임계값 스윕과 규칙 끄기 15줄.** 규칙마다 켜고 끌 때 결과가 바뀌는 방향과 크기가 문서와 같다. 다른 것은 "마지막 rep을 곧장 랙에 거는 벤치"(복귀율 0.7에서 0.905 대 0.998)다. 이 생성기는 거치대를 락아웃 3~12 cm 아래에 두어, 거치대 높이에서 멈추면 70%를 못 채우는 rep이 생긴다.

다시 만들면서 코어에서 고친 것: rep 값을 구하는 구간이 앞 rep까지 걸쳐, 둘째 rep부터 값이 한 rep씩 밀리던 문제(tests/test_core.py에 시험 추가). 이 수정 전의 속도 수치는 버렸다.

아직 다시 내지 않은 것: 한 녹화에 두 세트(세트 나누기 45초 규칙과 종목 변경 규칙), 마지막 rep 실패, 횟수가 오른 시점. 세트를 닫는 코드가 아직 없다.

## 3단계 첫 시험: 공개 영상 하나 (2026-10-19)

GitHub 공개 저장소 dw2kim/BarbellTrackingCode의 `test_squat.mov`(옆에서 찍은 스쿼트, 1080×1920, 60 fps, 22초)를 학습한 검출기 없이 돌렸다. 첫 프레임의 원판 박스만 손으로 주고, 그 뒤로는 원판 테두리 원 찾기와 KLT로 따라갔다. 영상은 저장소에 넣지 않았다.

- 횟수 4회. 영상을 눈으로 봐도 4회다 (바닥 9.2 / 11.9 / 14.7 / 17.4초). 언랙·워크아웃·리랙은 세지 않았다.
- ROM 63~69 cm, 내리는 시간 0.80~1.03초, 올리는 평균 속도 0.86~0.93 m/s. 정답 장비가 없어 절대값은 검증하지 못했다.
- 처음에는 KLT 점을 원판 전체에 뿌렸더니 원판 가운데의 ArUco 마커를 따라가 ROM이 95 cm로 나왔다. 마커(와 바 끝)는 원판보다 카메라 쪽으로 튀어나와 있어 보는 각도에 따라 원판과 따로 움직인다. 그래서 점을 원판 고리 부분(반지름 45~85%)에만 두고, 모델이 없을 때는 매 프레임 원판 테두리 원을 찾아 박스를 맞춘다. 학습한 검출기를 붙여도 같은 이유로 바 끝이 아니라 원판 테두리 박스를 써야 한다.
- 처리 속도 약 15 fps (CPU, 1080×1920, 원 찾기 포함).
- rep 3의 최저점 멈춤 0.14초는 원 찾기 잡음이 만든 작은 흔들림이다.

## 1단계: 세트 시험 (2026-10-18)

전체 표는 `results/sets.md`. 30 fps, 잡음 1 cm, 최종 / 라이브.

- **두 세트, 간격 68~163초 (400건).** 세트 수·종목·횟수가 모두 맞음 1.000 / 0.995. 라이브의 둘은 세트 닫기와 상관없다 (rep 하나 더 셈, 바닥 아래 이상치가 기준점을 옮겨 미완료 시도 하나가 세트로 남음).
- **같은 종목, 간격 24~55초 (400건).** 간격 43.9~54.9초는 두 세트, 24.1~44.0초는 한 세트로 합쳐진다 (문서 43.8~55.3 / 23.8~44.4). 합쳐진 것 중 횟수 합이 맞음 0.964 / 0.996. 틀린 것은 두 세트의 ROM이 달라 앞 세트 rep이 부분 rep으로 빠진 경우다.
- **스쿼트↔벤치 32~55초 0.995 / 0.998, 데드리프트가 낀 종목 변경 29~51초 1.000 / 1.000** (문서 0.984 / 1.000, 1.000 / 1.000). 틀린 것은 벤치 거치대가 락아웃보다 13 cm 넘게 낮아 리랙이 진행 중인 왕복으로 남은 채 원판이 사라지고, 스쿼트 랙에서 더 높게 다시 보일 때 rep으로 닫힌 경우다.
- **마지막 rep 실패 (스쿼트·벤치 600세트).** 횟수 1.000 / 1.000, 미완료 시도 1개로 표시 1.000 / 1.000.
- **횟수가 오르는 시점 (라이브).** 바가 다 돌아오기 0.31초 전 (중앙값, 5~95백분위 0.54~0.12초 전). 첫 rep 0.26초 전, 이후 0.32초 전 (문서 0.24초 전). 라이브 속도는 올리는 동작이 끝나고 0.57초 뒤 (95백분위 1.07초, 문서 약 0.5초, 1.2초).
- 종목이 바뀌면 바를 옮기는 5~15초 동안 원판이 안 보이고, 그 순간 라벨이 바뀐다고 뒀다. 같은 종목이면 바가 그 자리에 있다.
- 세트를 닫는 시계는 마지막 rep부터 잰다. 처음에는 미완료 시도에서도 시계를 다시 시작했는데, 벤치 거치대가 락아웃보다 13 cm 넘게 낮으면 리랙이 20초 뒤 미완료 시도로 닫히면서 시계가 다시 가서, 간격 44~55초의 약 6%(모두 벤치)가 한 세트로 합쳐졌다.

## 2단계: 비교 판정 시험 (2026-10-17)

전체 표는 `results/compare_rules.md`, 원자료는 `results/cmp_*.json`이다.

- **배수 표.** 문서 표 A·B·C 81칸과 모두 같다.

추적 공백을 보간하지 않으며 포즈 관측이 없으면 중앙값은 null이다.

시트는 각 0.5초 시점 이후 첫 포즈 실행 프레임을 사용한다.

`server.jobs`, `eval.counts`, `eval.plate_recall`에 `--device auto|cuda|cpu`가 있다.
기본 auto는 CUDA provider가 있으면 CUDA+CPU를 요청하고, 없으면 CPU만 요청한다.
CUDA 초기화 실패로 CPU가 활성화되면 auto는 CPU로 계속한다. cuda는 CUDA 활성화를
검사하고 runtime fallback을 끈다. cpu는 CPU만 요청하며 torch를 import하지 않는다.
CUDA를 요청할 때만 사용 가능한 ORT preload_dlls, 그 다음 선택적 torch import를 시도한다.
실제 활성 provider 목록을 `detector.providers`와 `result.json.detector_providers`에 남긴다.
목록은 활성 backend 정보이며 개별 연산의 GPU 배치를 측정한 값은 아니다.

`eval.counts --out`은 기존 디렉터리를 거부한다. `--root`는 CSV의 상대 경로 앞에 붙인다.
`team9.csv`는 원본 sets.csv에서 만든 파일 이름만 담으므로 root 아래에서 같은 이름을
재귀 탐색해 **유일하게 존재하는 파일만** 사용한다. 중복 이름은 오류이며, 운동 라벨로
폴더 이름을 추측하지 않는다. `quality=unrated`는 품질을 아직 따로 주석하지 않았다는 뜻이다.

각 영상에 rows/result/report와 `diagnostics.json`이 생긴다. `--debug`이면 타임라인을
만들고, 횟수가 틀린 영상에는 폭 540 디버그 mp4도 만든다. 요약은 counts.csv/summary.json이다.
`exact`는 세트 수와 무관하게 총 횟수 일치, 기존 `right`는 세트 하나이고 횟수 일치다.

### 진단 해석과 산출물

- `dets`: 검출기 반환 후보(confidence/NMS 적용 후)를 **별도 사본**에서 점수순 최대 10개 기록한다.
  `pick`은 그 목록의 0-based 순번이며, 후보 없음·원 찾기 사용·선택 후보가 기록 상한 밖이면 null이다.
  원래 후보 배열을 정렬하거나 상한으로 선택을 제한하지 않는다. `pick`은 tracker가 받아들였다는 뜻도 아니다.
- `used_ratio`: 현재 Track. `src_share` 분모는 전체 프레임이며 box가 없으면 none이다.
  초기 원 찾기의 src=det 표기는 기존 동작이며 모델 검출 성공으로 해석하지 않는다.
- `y_range`: used box 중심 y의 p95−p5 / used box 높이 중앙값. lost의 고정 box는 통계에서 제외한다.
  `jumps`는 이전 used 관측 대비 높이 ±25% 초과 또는 중심 이동 0.3×이전 높이 초과다.
  재획득·빠른 실제 움직임도 표시하므로 원판 교체 판정이 아니다.
- `moving_cands`: 현재 추적 box와 IoU<0.3인 후보를 IoU≥0.3으로 1:1 탐욕 연결한다.
  최대 5개 누락 프레임을 허용하고, 0.5초 이상·세로 범위가 자기 높이 중앙값의 0.3배 초과인
  궤적 수/시각이다. 실제 다른 원판 수, 운동 횟수 또는 정답 identity가 아니다.
- `wrist_r`: used 원판과 현재 프레임에서 보이는 가까운 손목의 상관이다. 2초 창은 쌍 10개 이상,
  원판 y 범위가 높이 중앙값의 0.1배 초과일 때만 계산한다. `wrist_seen` 분모는 used이며
  pose/kp 기록이 있는 프레임이다. 포즈 생략 프레임에 보간/이전 kp 복사는 하지 않는다.
  frame_h가 없으면 손목 통계는 미정이다. `near_wrist`의 선택적 frame_w로 가로 경계도 검사하며
  디버거는 result/video의 폭을 전달한다. frame_h만 넘기는 호출은 오른쪽 가로 경계를 알 수 없다.
- 타임라인은 원시·최종 높이, start~back 구간과 번호, 실제 세션 open/close를 표시한다.
